# Money Dev Kit provider research

Researched September 4, 2026. This note covers the provider; the companion migration note maps it to Last Pay Wins. No account was created, credentials installed, or payments sent.

## Fit and custody

Money Dev Kit (MDK) can replace the offline LND node. Its checkout SDK runs a new self-custodial Lightning node within the app's server infrastructure, wakes it via provider requests to receive payments, and manages channels and inbound liquidity through MDK's infrastructure. The app holds the wallet mnemonic in `MDK_MNEMONIC`; the old node does not need to be online. This removes personally operated node infrastructure, but the Next.js service still participates in receiving funds and must be reachable. Back up the mnemonic securely. [How MDK works](https://docs.moneydevkit.com/howitworks)

The homepage describes the product as public beta and quotes **2% per transaction**, without monthly/setup fees. At a 100-sat payment this implies 2 sats before any separate routing charges; confirm minimums and rounding with MDK. I found no clear published inbound minimum, maximum, or rate-limit guarantee. [Pricing](https://moneydevkit.com/)

## Packages and hosting

`npm view` reported `@moneydevkit/nextjs@0.22.0` as latest. Its published peer dependencies accept Next.js 15/16 and React 18/19. I downloaded, but did not install, the `nextjs` and `core` 0.22.0 tarballs and inspected their published JavaScript/type declarations. The GitHub snapshot used for source references is `62d045c5938495891f7ffa9481164f28a815074a`; its package version says `0.22.0-beta.0`, so do not equate Git main with the published version. The behaviors highlighted below were checked against published 0.22.0 where relevant. [Published package metadata](https://registry.npmjs.org/@moneydevkit/nextjs/0.22.0), [Git package](https://github.com/moneydevkit/mdk-checkout/blob/62d045c5938495891f7ffa9481164f28a815074a/packages/nextjs/package.json)

The documented integration requires `MDK_ACCESS_TOKEN`, `MDK_MNEMONIC`, the `/api/mdk` route export, and the `withMdkCheckout` Next.js config wrapper. The optional checkout UI is rendered in the merchant app at `/checkout/[id]`; the term "hosted checkout" does not imply that the merchant server is uninvolved. [Next.js guide](https://docs.moneydevkit.com/nextjs)

The config wrapper externalizes and traces native `@moneydevkit/lightning-js` binaries. Run this integration in a Node.js route, not an Edge function or browser. The receiving handler opens an outbound WebSocket control connection, obtains a lease before constructing the node, and runs an event loop with a 60-second quiet grace period and 300-second lifetime. Check production function duration, native binary packaging, outbound connectivity, and cold-start behavior. The business-event webhook's 30-second timeout is a different endpoint/concern. [Next plugin](https://github.com/moneydevkit/mdk-checkout/blob/62d045c5938495891f7ffa9481164f28a815074a/packages/nextjs/src/next-plugin.ts), [Receive handler](https://github.com/moneydevkit/mdk-checkout/blob/62d045c5938495891f7ffa9481164f28a815074a/packages/core/src/handlers/webhooks.ts)

## Retaining the existing QR payment interface

The public `@moneydevkit/core` entry point exports `createCheckout`, `getCheckout`, and `confirmCheckout`. `createCheckout({ type: "AMOUNT", currency: "SAT", amount, metadata })` returns a result containing a full checkout. A confirmed amount checkout automatically progresses to invoice minting. `@moneydevkit/nextjs/server` does **not** directly export these create/read helpers; add `core` as an explicit dependency if using them. [Core exports](https://github.com/moneydevkit/mdk-checkout/blob/62d045c5938495891f7ffa9481164f28a815074a/packages/core/src/index.ts), [Actions](https://github.com/moneydevkit/mdk-checkout/blob/62d045c5938495891f7ffa9481164f28a815074a/packages/core/src/actions.ts), [Next server exports](https://github.com/moneydevkit/mdk-checkout/blob/62d045c5938495891f7ffa9481164f28a815074a/packages/nextjs/src/server/index.ts)

A pending checkout provides `invoice.invoice` (BOLT11), `invoice.paymentHash`, `invoice.expiresAt`, `invoice.amountSats`, and the checkout ID. Therefore preserving Last Pay Wins' QR/deep-link presentation appears feasible without imposing a separate checkout screen. The adapter must handle unconfirmed/expired checkouts, not assume every create response already has an invoice. [Checkout schema](https://github.com/moneydevkit/mdk-checkout/blob/62d045c5938495891f7ffa9481164f28a815074a/packages/api-contract/src/schemas/checkout.ts), [Invoice schema](https://github.com/moneydevkit/mdk-checkout/blob/62d045c5938495891f7ffa9481164f28a815074a/packages/api-contract/src/schemas/invoice.ts)

The high-level `createCheckout` helper has no expiry parameter. The lower-level `mintInvoice` contract accepts `expirySecs`, while the local node helper defaults to 15 minutes. Retaining the app's existing five-minute invoice lifetime needs a supported create/confirm/mint sequence or a deliberate expiry change; do not simply keep a five-minute browser timer against a longer-lived invoice. [Checkout contract](https://github.com/moneydevkit/mdk-checkout/blob/62d045c5938495891f7ffa9481164f28a815074a/packages/api-contract/src/contracts/checkout.ts), [Node invoice helper](https://github.com/moneydevkit/mdk-checkout/blob/62d045c5938495891f7ffa9481164f28a815074a/packages/core/src/lightning-node.ts)

## Settlement and winner correctness

MDK offers separate `checkout.completed` business webhooks. Verify the raw body with `standardwebhooks` and `MDK_WEBHOOK_SECRET`; headers include `webhook-id`, `webhook-timestamp`, and `webhook-signature`. Deduplicate events durably. Retries are documented at 5 seconds, 5 minutes, 30 minutes, 2 hours, and 8 hours; five consecutive failures across events disable the endpoint. Processing times out at 30 seconds. Persist before acknowledging success. [Webhooks](https://docs.moneydevkit.com/webhooks)

The example event includes metadata and amounts, but **does not show a checkout ID or payment hash**. Its envelope has an event `timestamp`; the header timestamp is dispatch time. Neither is documented as authoritative Lightning settlement time. Put an app-generated payment reference in metadata and persist its checkout binding. On receipt, read that bound checkout server-side before crediting the game. [Webhook payload](https://docs.moneydevkit.com/webhooks)

The SDK uses `PAYMENT_RECEIVED` for successful checkout state, whereas webhook examples show `COMPLETED`. Neither checkout nor invoice schemas exposes a `paidAt`/`settledAt` field. Consequently, arrival order of webhooks cannot safely stand in for payment order. For a last-payer-wins game, decide how settlement order, delayed events, and the round deadline interact before enabling prizes; ask MDK whether it can supply a durable settlement timestamp/sequence and reconciliation API. [Checkout schema](https://github.com/moneydevkit/mdk-checkout/blob/62d045c5938495891f7ffa9481164f28a815074a/packages/api-contract/src/schemas/checkout.ts), [Invoice schema](https://github.com/moneydevkit/mdk-checkout/blob/62d045c5938495891f7ffa9481164f28a815074a/packages/api-contract/src/schemas/invoice.ts)

**Source-level reliability caveat:** the receive handler catches failures when reporting a received Lightning payment to MDK's checkout API and logs them. Its TODO explicitly acknowledges that the customer/provider checkout may remain unconfirmed after money was received. Published 0.22.0 contains this behavior; this is a source observation, not a demonstrated production failure. Application polling can recover a lost business webhook when provider state is current; it cannot alone repair stale provider settlement state. Confirm the provider's recovery path before handling a real prize pot. [Receive-reporting implementation](https://github.com/moneydevkit/mdk-checkout/blob/62d045c5938495891f7ffa9481164f28a815074a/packages/core/src/handlers/webhooks.ts)

## Winner payouts and withdrawals

MDK supports manual withdrawals, automatic sweeps after incoming payments, and programmatic payouts. For a prize pot, retain funds and select programmatic payouts; automatic full-balance sweeps would move away funds needed to pay winners. Programmatic payouts default to a 1,000,000-sat per-request cap and 5,000,000-sat rolling daily budget. Manual/automatic withdrawals use `WITHDRAWAL_DESTINATION`, accepting Lightning addresses, LNURL, or BOLT12. Routing fees require a reserve. [Payouts](https://docs.moneydevkit.com/dashboard/payouts)

`programmaticPayout` accepts an app-controlled destination and stable `idempotencyKey`; use a persisted round-payout ID. Supported destinations include BOLT11, BOLT12, and LNURL/Lightning address. An accepted dispatch is **not settlement**: call `waitForPayoutResult` and distinguish `REQUESTED`, `SUCCESS`, and `FAILED`; the application must persist/reconcile uncertain outcomes without creating a new idempotency key. [Server implementation](https://github.com/moneydevkit/mdk-checkout/blob/62d045c5938495891f7ffa9481164f28a815074a/packages/core/src/server.ts), [Payout contract](https://github.com/moneydevkit/mdk-checkout/blob/62d045c5938495891f7ffa9481164f28a815074a/packages/api-contract/src/contracts/checkout.ts)

## Testing and questions to resolve

For live local tests, the docs require an internet-accessible development server (for example, ngrok) and the corresponding app URL in the dashboard. Use a separate development app so changing that URL does not redirect production wakeups. [Troubleshooting](https://docs.moneydevkit.com/troubleshooting)

Source also includes `sandbox` checkout state, `MDK_PREVIEW`/`NEXT_PUBLIC_MDK_PREVIEW` test flags, and a preview-only fake-payment route. Do not enable preview flags on a production app: the source explains that this path can assert a payment without Lightning settlement. Separate test credentials and funds, and reject sandbox events when crediting live games. The source contains signet/staging defaults under `MDK_NETWORK=signet`, but public onboarding/access guarantees for this environment were not established. [Preview detection](https://github.com/moneydevkit/mdk-checkout/blob/62d045c5938495891f7ffa9481164f28a815074a/packages/core/src/preview.ts), [Preview route](https://github.com/moneydevkit/mdk-checkout/blob/62d045c5938495891f7ffa9481164f28a815074a/packages/core/src/handlers/pay_invoice.ts), [Network configuration](https://github.com/moneydevkit/mdk-checkout/blob/62d045c5938495891f7ffa9481164f28a815074a/packages/core/src/mdk-config.ts)

Before production, resolve authoritative settlement ordering/reconciliation, five-minute invoice expiry support, actual 100-sat receipt fees/minimums, and payout routing reserves and caps. A focused integration spike should exercise receipt while the payer closes the browser, duplicate/delayed/out-of-order events, cold starts, near-deadline payments, fee accounting, and payout timeout recovery.
